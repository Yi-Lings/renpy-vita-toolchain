# 启动优化计划：70 秒到底花在哪

> 2026-11-01，Angel Sex Pet / PS Vita 3.65
> 目标：分析 `启动 ≈ 70s` 的构成，判断哪些能优化、哪些是物理下限。

---

## 0. 结论摘要

**`Loading script` 一项占 73%（52.01s），且是纯 CPU 开销（AST 反序列化），不是 I/O。**

- 实测 PC 上同一份数据 `Loading script = 1.38s`，Vita 是 52.01s，**比值 38×** —— 与两者 CPU 差距一致，说明瓶颈在 CPU 而不是存储卡。
- 归档里只有 **37 个 `.rpyc`，合计 2.17 MB**。读 2 MB 不可能要 52 秒。

**乐观预期**：现有手段全部用上，70s → **约 55–60s**（-15~20%）。
**剩下的 52s 属于「Ren'Py 在 444MHz CPU 上反序列化脚本」的物理成本**，不改引擎很难再降。

## 2. `Loading script` 在做什么

`renpy/main.py:482` → `renpy.game.script.load_script()`。这个计时点包住的就是它：

```python
# renpy/script.py:264
def load_script(self):
    script_files.sort()
    for fn, dir in script_files:
        self.load_appropriate_file(".rpyc", ".rpy", dir, fn, initcode)
    self.translator.chain_translates()
```

每个文件内部（`finish_load`，`script.py:376`）：

1. `renpy.ast.chain_block(stmts)` —— 串起语句链表
2. 遍历 `i.get_children(...)` 收集**全部**语句（递归整棵树）
3. `translator.take_translates(all_stmts)` —— 收集翻译
4. `self.update_bytecode()` —— 编译 Python 代码对象
5. 逐节点循环处理

**主要成本是第 0 步之前：`pickle.loads` 反序列化 2.17 MB 的 AST。**
Python 2 的 pickle 要逐条指令创建对象、调用 `__setstate__`，在 444MHz 上是纯 CPU 苦工。

### 2.1 交叉验证

| 环境 | Loading script |
|---|---|
| PC（同版本 SDK，同数据） | **1.38s** |
| Vita | **52.01s** |
| 比值 | **38×** |

Vita 的 CPU（444MHz ARM）相对 PC 大致就是这个倍数。**说明这一项没有异常，就是慢在算力。**

### 4.3 重点怀疑：每次启动都在重编译 Python 代码

`Save bytecode. took 0.92s` 说明 `bytecode_dirty` 为真
（`script.py:889`：`if self.bytecode_dirty:` 才写盘）。

而 `bytecode_dirty` 只在一种情况下置位（`python.py:826`）：**缓存里找不到对应的 PyCode**。
也就是说 **每次启动都有一批 Python 代码在重新编译**，编译时间算在 `Loading script` 里。

可能原因：游戏的 `.rpyc` 是 **7.3.5 编译的**，而运行时是 **7.4.9.0u**，
`python.py:771` 的缓存 key 含 `MAGIC`，版本不同 → 全部 miss → 每次重编。

**这条如果成立，收益可能是几十秒里的一大块。**
验证方法：在 `Loading script` 内部按文件计时，看哪些文件的 `update_bytecode` 慢。

### 4.4 不建议做

| 项 | 原因 |
|---|---|
| 合并 `.rpyc` 成少数大文件 | 反序列化总量不变，收益≈0，且破坏工具链 |
| 改 `eboot.bin` 做懒加载 | 需要改引擎源码 + 重新交叉编译，风险极高 |
| 超频到 500MHz | 收益 <13%，且影响续航和稳定性 |
| 压缩 `.rpyc` | 解压也要 CPU，在慢 CPU 上得不偿失 |

## 5. 下一步：先测量，再动手

现在缺的是 **`Loading script` 内部的逐文件分解**。要拿到它需要一次**测量专用构建**：

在 `renpy.py`（6,722 B，随包发布）里，于 `renpy.main.main()` 之前包装
`renpy.script.Script.load_appropriate_file`，把每个文件的耗时写进 `log.txt`：

```python
import time
_orig = renpy.script.Script.load_appropriate_file
def _wrap(self, compiled, source, dir, fn, initcode):
    t0 = time.time()
    try:
        return _orig(self, compiled, source, dir, fn, initcode)
    finally:
        renpy.write_log("BOOT %7.3fs  %s", time.time() - t0, fn)
renpy.script.Script.load_appropriate_file = _wrap
```

> ⚠ `renpy.py` 是「原版尺寸 6,722 B」的受保护文件（踩坑总结）。
> 这个改动**只用于测量构建**，测完必须换回原版。

拿到分解后可以立刻回答：
- 是 unpickle 慢，还是 `update_bytecode` 慢？
- `tl/jp` 到底占多少？
- 有没有某个文件异常（比如 `screens.rpyc`）
