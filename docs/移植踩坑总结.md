> 记录 2026-10-30/31 两天的完整过程：从"这批游戏能不能移植"到跑通第一个 Ren'Py 包。
> 所有结论都来自实测，标注了哪些是已验证、哪些仍是推测。

## 0. 一句话结论

**能不能移植，只取决于引擎有没有现成的 Vita 运行时**，跟游戏大小、画面复杂度关系不大。

| 引擎 | 运行时 | 状态 |

## 1. 网络：GitHub 被 hosts 屏蔽

**症状**：`api.github.com` 解析到 `127.0.0.1`，所有 GitHub 访问失败。

**原因**：`C:\Windows\System32\drivers\etc\hosts` 里有大量 `127.0.0.1 github.com #S302` 条目。

**绕过方法（不改 hosts）**：

```powershell
curl --resolve api.github.com:443:20.205.243.168 https://api.github.com/...
```

各域名真实 IP（用 `Resolve-DnsName <host> -Server 8.8.8.8` 查）：

| 域名 | IP |
|---|---|
| github.com | 20.205.243.166 |
| api.github.com | 20.205.243.168 |
| codeload.github.com | 20.205.243.165 |
| raw.githubusercontent.com | 185.199.109.133 |
| objects / release-assets.githubusercontent.com | 185.199.109.133 |

**注意**：`raw.githubusercontent.com` 的 IP 被 TLS 层阻断（TCP 通但握手失败），改用 `codeload.github.com` 下整包 tarball 更可靠。

**下载大文件的坑**：release 资源走 `release-assets.githubusercontent.com`，直连只有 ~34 KB/s 且经常断。`curl --retry` 会**从头重下**（`-o` 截断），必须自己做分块断点续传。

**PowerShell 传参坑**：`$opts = '--resolve host:443:ip'` 会作为**单个参数**传给外部程序，必须用数组 `@('--resolve','host:443:ip')` 再 splat。

## 2. VPK 打包：三个必须遵守的规则

### 2.1 路径必须用正斜杠

`[System.IO.Compression.ZipFile]::CreateFromDirectory()` 在 .NET Framework 下会把条目名写成 `game\demo.rpa`，**VitaShell 无法识别**。

用 Python `zipfile` 打包，条目名天然是 `/`。

### 2.2 `sce_sys/param.sfo` 必须是第一个条目

对照能正常安装的 `CTManager.vpk`，首条目是 `sce_sys/param.sfo`。

### 2.3 文件名用纯 ASCII

带中文的 VPK 文件名（如 `..._运行时only.vpk`）会导致安装失败。

## 3. `0x8010113D`：LiveArea 图片格式

**这是最耗时的一个坑，卡了整整一晚。**

### 症状

安装进度走到 **99%** 然后失败，错误码 `0x8010113D`。清理目录、重启、换 TITLE_ID 全部无效。

### 原因

> `0x8010113D` = **"incorrect LiveArea asset image formats"**

Vita 安装器**只接受 8-bit 索引色 PNG**。用 Pillow 默认保存的 24 位真彩色（`colortype=2`）会被拒绝。

### 硬性规格

| 文件 | 尺寸 | 色彩类型 | alpha |
|---|---|---|---|
| `icon0.png` | 128×128 | colortype=3, bitdepth=8 | **不可有** |
| `pic0.png` | **960×544** | colortype=3, bitdepth=8 | 不可有 |
| `bg.png` | 840×500 | colortype=3, bitdepth=8 | **不可有** |
| `startup.png` | 280×158 | colortype=3, bitdepth=8 | 可有 |

- 必须**非交错**（interlace=0）
- 文件名是 **`bg.png`**，不是 `bg0.png`（大多数教程写错）
- `pic0.png` 尺寸必须是 960×544，错一点就失败

### 转换代码

```python
img.convert("RGB").quantize(colors=256, method=Image.MEDIANCUT).save(path, "PNG", optimize=True)
```

### 验证方法

直接读 PNG 的 IHDR：

```python
d = open(path, "rb").read()
w, h = struct.unpack(">II", d[16:24])
bit, ctype, interlace = d[24], d[25], d[28]
# 要求 ctype == 3 且 bit == 8 且 interlace == 0
```

### 参考

- `thcolin/gamepad-media-center-aggregator` PR #31（有真机验证）
- `bee-san/Rubi_for_vita` PR #23
- `Hammerill/livearea-specs`

## 4. 安装方式：三种格式的取舍

| 格式 | 原理 | 适用 | 结论 |
|---|---|---|---|
| **VPK** | VitaShell 解包到 `ux0:/app/TITLEID` + 写 `app.db` | 自制程序 | ✅ **最可靠** |
| **NoNpDrm** | 文件夹直接拷到 `ux0:/app/TITLEID` | 零售解密 dump | ⚠️ 自制程序**不会注册气泡** |
| **mai** | MaiDumpTool 安装 | 零售 dump | ❌ 自制程序不适用 |

### 4.1 为什么 mai 格式对自制程序无效

真正的 mai 包有 `mai_moe/`：

```
mai_moe/
├─ mai.suprx          85.8 KB   免授权插件本体
├─ eboot_origin.bin   16.5 MB   原始加密 eboot 备份
└─ load_type.mai
```

`eboot_origin.bin` 存的是**原始加密 eboot**，MaiDumpTool 靠它做签名绕过。自制 SELF（VitaSDK 产出）没有"原始加密版本"可还原，补不出来。

另外真 mai 包的 `CATEGORY` 是 `gp`，还有 `sce_module/`（Sony 系统模块），自制程序都不需要。

### 4.2 文件夹直拷不注册气泡 —— 已解出配方

系统在开机扫描 `ux0:/app` 时，会读取 `sce_sys` 并做授权检查，**结构不完整的目录直接跳过**。

从机器上已成功运行的移植包（`G:\app\AIME*`，Artemis 引擎移植）逆向出的完整结构：

```
ux0:/app/<TITLE_ID>/
├─ eboot.bin
├─ sce_module/          ← 5 个通用系统模块，缺了不注册
│  ├─ libc.suprx            200.7 KB
│  ├─ libface.suprx          70.2 KB
│  ├─ libfios2.suprx        117.8 KB
│  ├─ libsmart.suprx       1524.9 KB
│  └─ libult.suprx           48.9 KB
└─ sce_sys/
   ├─ icon0.png         128x128, 8-bit 索引色
   ├─ pic0.png          960x544
   ├─ param.sfo         1328 字节（零售布局，不是 mksfoex 的 912）
   ├─ about/right.suprx
   ├─ manual/001~003.png
   ├─ package/head.bin  1072 字节，内含 content ID
   └─ livearea/contents/{background.png, startup.png, template.xml}
```

**关键点：**

1. **`param.sfo` 必须是 1328 字节的零售布局**，18 个字段，比 mksfoex 生成的多出
   `GC_RO_SIZE`、`GC_RW_SIZE`、`PUBTOOLINFO`、`REGION_DENY`、`SAVEDATA_MAX_SIZE`，
   且**没有** `BOOT_FILE`、`EBOOT_*`、`LAREA_TYPE`、`NP_COMMUNICATION_ID`。

2. **`TITLE_ID` = 文件夹名**，但 `CONTENT_ID` 保留零售格式的值，两者不必一致。

3. **`package/head.bin` 是合成文件**，偏移 48 处嵌着
   `EP9000-<TITLE_ID>_00-XXXXXXXXXXXXXXXX`（16 个 X 是占位符，说明不是真实签名）。
   按同样格式生成即可。

4. **固件版本字段要降**：参考包写的是 `PSP2_DISP_VER=03.690` / `PSP2_SYSTEM_VER=0x03690000`，
   在 3.65 上要改成 `03.600` / `0x03650000`。

#### param.sfo 字段布局（终于搞对了）

16 字节 entry：

```
key偏移(2) | fmt(1) | len(1) | max_len(4) | ?(4) | data偏移(4)
```

**`data_offset` 在 +12，不是 +8** —— 这是之前一直解析出乱码的原因。
（+8 那个字段含义不明，实测与数据无关，原样保留即可。）

文件头 20 字节：`magic(4)=0x46535000 | version(4)=0x101 | key表偏移(4) | data表偏移(4) | 条目数(4)`

#### 改造工具

`tools/make_nonpdrm_pkg.py` —— 以可运行的参考包为模板，等长替换
`TITLE_ID` / `CONTENT_ID` / `TITLE` / `STITLE` / `PSP2_DISP_VER`，
并复制 `sce_module/`、`about/`、`manual/`、生成 `package/head.bin`。

因为全部是**等长原地替换**，不需要重写 sfo，避开了 pickle/序列化的所有坑。

### 4.3 结论：用 VPK，但可以拆开装

VPK 慢的本质是"在 Vita 上解包几百 MB"。拆开就快：

1. 装**只含运行时的小 VPK**（约 14 MB），几秒完成，气泡和 `app.db` 记录都有了
2. 用 FTP 把游戏数据（`.rpa`）传进 `ux0:/app/TITLEID/game/`

最终磁盘结构和你手拷的一模一样，只是快一个数量级。

## 5. `libshacccg.suprx`：GL 程序的硬前置

**症状**：HardRPG 启动即崩（`C2-12828-1`）；renpy-vita 卡在启动图。

**原因**：Vita 上所有 GL 程序编译着色器都要走 Sony 的 shader 编译器 `libshacccg.suprx`，必须放在 `ur0:/data/`。

**安装**：
- 最简单：装 `VitaDB-Downloader.vpk`，里面有一键安装
- 或者：`ShaRKF00D.vpk`（需要先装 PSM 运行时 1.00 → 2.00 → 2.01，顺序不能错）

**装完必须重启。**

⚠️ 这个文件是 **HardRPG 和 renpy-vita 共同的前置条件**，但很容易在排查时被忽略。

## 6. 认识 `pic0.png`：它不是游戏画面

**这是最关键的一个认知点。**

`pic0.png` 是 Vita 在**应用加载期间**显示的静态图。如果屏幕上长时间停在这张图上，说明：

> **引擎根本没启动**，不是游戏画面卡住了。

**诊断价值**：把 `ux0:/app/TITLEID/game` 改名，再启动。
- 图还在 → 是 `pic0.png`，引擎没起来，问题在运行时
- 图没了/变了 → 是引擎画的，问题在游戏数据

这个 10 秒测试能一刀切开"运行时问题"和"游戏数据问题"，比猜快得多。

## 7. renpy-vita 的引擎补丁

### 发现过程

对照 2026-10 的可用移植 `haskou/subahibi-psvita`（同样是 Python 2.7），逐字节比对运行时：

| 文件 | 可用版 | DistTool 原版 | 结论 |
|---|---|---|---|
| `eboot.bin` | 7,732,057 | 7,732,057 | **完全相同** |
| `module/libGLESv2.suprx` | 1,994,745 | 1,994,745 | **完全相同** |
| `module/libgpu_es4_ext.suprx` | 41,529 | 41,529 | **完全相同** |
| `module/libIMGEGL.suprx` | 100,253 | 100,253 | **完全相同** |
| `module/libpvrPSP2_WSEGL.suprx` | 17,869 | 17,869 | **完全相同** |
| `renpy/loader.pyo` | 24,413 | 23,217 | 差 +1,196 |
| `renpy/script.pyo` | 18,694 | 18,260 | 差 +434 |
| `renpy/display/core.pyo` | 73,333 | 73,869 | 差 -536 |
| `renpy.py` | 6,835 | 6,722 | 多两个环境变量 |

**结论**：eboot 和图形模块完全一样，差的只有三个引擎模块。`loader` 管归档加载、`script` 管脚本加载——正是 issue #8 报错的地方（`Loading script took 163.37s` 然后崩溃）。

### 真正的根因：`renpy/common` 缺预编译的 `.rpyc`

上面那三个 `.pyo` 的差异**不是**关键。真正的差异在别处，是通过一个
真机能跑的包（`RNPYSS001`，Sakura Succubus 5 移植）比对出来的：

| 位置 | 文件数 | `.rpy` | `.rpyc` |
|---|---|---|---|
| 能跑的包 | **336** | 54 | **54** |
| Distribution Tool 自带 | 267 | 54 | **0** |

**DistTool 的 `renpy/common` 里一个 `.rpyc` 都没有，只有 `.rpy` 源码。**

后果：`app0:` 是只读挂载，Ren'Py 没法把编译产物写回磁盘，于是**每次启动都要在 Vita 上现场编译 54 个 common 脚本**。这就是"卡在 pic0 静态图几分钟然后崩溃"的真正原因。

issue #8 里那句 `Loading script took 163.37s` 是同一个问题；而能跑的包里预编译好了，日志显示只需 `37.48s`。

### 修正做法

**不要自己打补丁，直接把一个能跑的包的 `renpy/common` 整个复制过来。**

```
你的包/renpy/common/   ←   能跑的包/renpy/common/   （336 个文件，含 54 个 .rpyc）
```

同时 `renpy.py`（6,722 字节）和 `lib/python27.zip`（3,919,486 字节）都要保持
**DistTool 原版**，不要替换成别的移植里的版本——我之前换过，反而更糟。

### 验证过的可用结构

```
ux0:/app/<TITLE_ID>/
├─ eboot.bin            7,732,057
├─ renpy.py             6,722          ← 原版
├─ lib/python27.zip     3,919,486      ← 原版
├─ module/*.suprx ×4
├─ renpy/common/        336 个文件，含 54 个 .rpyc   ← 关键
├─ game/                游戏数据（.rpa 等）
└─ sce_sys/             icon0 / pic0 / param.sfo(912) / livearea/ / package/head.bin
```

### Ren'Py 版本适用范围（实测）

| 游戏 | Ren'Py 版本 | 结果 |
|---|---|---|
| **Angel Sex Pet** | **7.3.5** | ✅ **真机跑通（2026-10-31）** |
| Sakura Succubus 5 | **7.4.8** | ✅ 真机日志确认可跑 |
| Maid Mansion | 7.4.11 | ❌ 未验证（100% webp，另说） |

运行时是 **Ren'Py 7.4.9**。实测 **7.3.5 和 7.4.8 都能跑**——
之前"7.3.5 太老跑不了"的结论是错的，真正原因是缺 `.rpyc`、

## 7.5 `script_version.txt` 被汉化组塞了水印（2026-10-31 新发现）

**这一批 miel / norn 的"SEEACG"汉化版，把推广水印直接追加进了
`game/script_version.txt`：**

```
(7, 3, 5)\r\n
\r\n
更多资源:SEEACG.COM      ← GBK 字节，32 字节的文件
```

正常应该只有 9~11 字节：`(7, 4, 8)\n`。

### 为什么这很致命

`renpy/common/00compat.rpy` 是这么读的：

```python
with renpy.file("script_version.txt") as f:
    script_version = f.read()
config.script_version = ast.literal_eval(script_version)
renpy.write_log("Set script version to: %r", config.script_version)
```

`ast.literal_eval` 拿到的是**整个文件内容**，不是第一行。多出来的中文行
直接抛 `SyntaxError`，而外面包着 `except: pass`，于是：

1. 日志里**永远不会出现** `Set script version to:`；
2. `config.script_version` 保持 `None`，`compat()` 恒为假，
   整个兼容层被跳过。

### 排查时的陷阱

看到日志停在 `Importing _renpysteam` 后面没有 `Set script version to:`，
很容易判断成"崩在这一行之前"。**其实这一行只是没打出来而已**，
真正的崩溃点在更后面。这是 2026-10-31 那轮误判的直接原因。

### 处理

```powershell
python tools/fix_script_version.py <游戏目录> --write
```

17 个 miel/norn 游戏**全部**中招（都是 32 字节、同一句水印），
打包前必须先跑一遍。

## 7.6 游戏自带「首发联网上报」，在 Vita 上必崩（2026-10-31 确认）

这是 Angel Sex Pet 卡在 pic0 的**真正原因**，也是这批 Cherry Kiss /
Miel 系游戏的通病。反编译 `splashscreen.rpyc` 后可以看到：

```python
init -3 python:
    persistent.jp_installed = False
    if not persistent.data_checked:
        import requests
        userdata = requests.get('http://ipinfo.io/json').json()
        useranalytics = requests.post('http://<厂商端点>', data=userdata)
        persistent.jp_ipcountry = userdata['country']
        persistent.data_checked = True
```

发行商内嵌的遥测：**首次启动同步发 HTTP 请求**。

Vita 上必然失败：

* 宿主 `python27.zip` 里没有 `_ssl`，也没有 certifi 证书包；
* `app0:` 只读，requests 写不了缓存；
* 抛的是**未捕获异常**，直接把 init 阶段打死。

### 崩溃 dump 里的铁证

`ux0:data/psp2core-*.psp2dmp` 是 gzip 的 ELF core，解压后在内存里能直接
搜到 `ipinfo.io`、`/json`、`user-agent`、`accept`、`certifi`、
`_ssl` 这些字符串——正是 requests 构造请求时的数据结构。
`THREAD_REG_INFO` 里的 PC 指向 Python 解释器，`MODULE_INFO` 里
只有 `libIMGEGL / libgpu_es4_ext / SceLibc / ... / eboot.elf`，
没有第三方模块。

### 为什么 Yuu 的 Sakura 5 能跑

| | Sakura Succubus 5 | Angel Sex Pet |
|---|---|---|
| `splashscreen.rpyc` | 只有 `label splashscreen` | **`init -3` 里联网上报** |

差别就在这一处。所以之前"运行时/固件不兼容"的判断是错的。

## 7.8 精准移植链条（每一步都可复现）

以 Angel Sex Pet 为例，从零到能玩。

### 前置条件

```
设备：PS Vita 3.65 变革（Enso）
插件：nonpdrm.skprx（NoNpDrm 游戏用）
关键文件：ur0:/data/libshacccg.suprx（GL 程序必需，缺了必崩）
PC：Ren'Py 7.4.9 SDK（用来编译 .rpyc）
```

### 步骤 1｜准备运行时（一次做好，所有 7.x 游戏通用）

运行时 = DistTool 的 Assets + 一个能跑的包的 `renpy/common`。

```
ux0:/app/<TITLE_ID>/
├─ eboot.bin            7,732,057    DistTool 原版
├─ renpy.py             6,722        DistTool 原版（不要改）
├─ lib/python27.zip     3,919,486    DistTool 原版（不要改）
├─ module/              4 个 .suprx   DistTool 原版
├─ renpy/common/        336 文件 / 54 个 .rpyc   ← 从能跑的包复制
└─ game/                游戏数据
```

`renpy/common` 一定要**整目录复制**能跑包的版本。DistTool 自带的那份一个
`.rpyc` 都没有，`app0:` 只读又写不回编译产物，等于每次启动都在 Vita 上
现场编译 54 个脚本。

### 步骤 2｜检查并清理游戏数据

```powershell
# 2.1 汉化水印（17 个 miel/norn 游戏都有）
python tools/fix_script_version.py <游戏目录>          # 检测
python tools/fix_script_version.py <游戏目录> --write  # 修正

# 2.2 首发联网上报（11 个游戏有）
python tools/fix_telemetry.py <游戏目录>               # 检测
# 生成补丁见步骤 3
```

检测结果是 `(7, 3, 5)\r\n\r\n更多资源:SEEACG.COM` 这类就说明中招了，
必须清成 9~11 字节。

### 步骤 3｜生成跳过上报的补丁

补丁源码（`init -10` 比上报块的 `init -3` 更早）：

```python
init -10 python:
    persistent.data_checked = True
```

**必须用 Ren'Py SDK 编译**，不能手写：

```powershell
# 建一个临时项目，把补丁放进 game/，跑 lint 让它编译
renpy.exe <临时项目> lint
# 产物：game/psv_skip_telemetry.rpyc（794 字节，version=5003000）
```

版本常量必须是 **5003000**（`0x4C56F8`），和 Vita 运行时一致，
否则 Ren'Py 会判定版本不符直接拒绝加载。

验证方法：解压 rpyc 的第一个 slot，看 `version` 后面那个 4 字节整数。

### 步骤 4｜组装 game 目录

```
game/
├─ archive.rpa          游戏主脚本
├─ img_resource.rpa     CG
├─ gui_resource.rpa     界面素材
├─ sfx_resource.rpa     音频
├─ dlc_japanese.rpa     DLC（可选）
├─ script_version.txt   清理过
└─ psv_skip_telemetry.rpyc   步骤 3 的产物
```

### 步骤 5｜生成 sce_sys

```powershell
python tools/make_scesys_generic.py <sce_sys目录> <logo.png> [alt.png] "标题"
```

硬性规格（不符合就 `0x8010113D`）：

| 文件 | 尺寸 | 要求 |
|---|---|---|
| `icon0.png` | 128×128 | colortype=3, bit=8, 无 alpha |
| `pic0.png` | 960×544 | 同上 |
| `livearea/contents/bg.png` | 840×500 | 同上 |
| `livearea/contents/startup.png` | 280×158 | 可有 alpha |

`param.sfo` 用 `vita-mksfoex -s TITLE_ID=XXXXXXXXX -d ATTRIBUTE2=12 -s APP_VER=01.00 "标题"`，
产出 912 字节即可（不必用 1328 字节的零售布局——实测 912 字节也能注册气泡）。

`package/head.bin` 从能跑的包复制 1072 字节，把偏移 48 处的
`EP9000-<TITLE_ID>_00-XXXXXXXXXXXXXXXX` 等长替换。

### 步骤 6｜装到设备

**推荐：拆开装**

1. 打一个只含运行时的 VPK（约 14 MB），VitaShell 安装 → 气泡和 `app.db` 记录都有了
2. 用 USB（VitaShell 的 USB 模式，挂成盘符）把 `game/*.rpa` 直接拷到
   `ux0:/app/TITLEID/game/`

不要试图文件夹直拷注册气泡——在 3.65 上验证过两次都失败。

### 步骤 7｜验证

启动后读 `ux0:/app/TITLEID/log.txt`，对照：

| log 行 | 含义 |
|---|---|
| `Set script version to: (x, y, z)` | 水印已清 |
| `Running init code took ...` | 没有初始化期崩溃（上报块已跳过） |
| `Initializing gles renderer:` | 引擎起来了 |
| `Screen sizes: virtual=...` | 渲染器正常 |

**注意**：这几行缺任何一行都不一定意味着崩在那里。
`Set script version` 缺失 = 水印没清；`Running init code` 缺失 = init 里崩了。
真实崩溃点往往在**最后一行日志之后的几百毫秒**，因为日志是行缓冲，
缓冲区里的内容随进程一起没了。

### 步骤 8｜崩溃时怎么查

1. **读 `log.txt`** —— 最后一行是最后被 flush 的内容，不是崩溃点
2. **解 `ux0:/data/psp2core-*.psp2dmp`** —— gzip 的 ELF core，
   解压后在内存里搜可疑字符串（我们就是靠搜到 `ipinfo.io` 定位的）
3. **反编译 `.rpyc`** —— `unrpyc` 能把 rpyc 还原成 .rpy，
   直接看 init 块里干了什么
4. **PC 上用同版本 SDK 复现** —— `renpy.exe <project> lint` 会执行 init 代码，
   异常信息比 Vita 上详细得多

## 7.9 性能优化（2026-10-31）

### 卡顿的根因

Vita 的 GPU 是 **PowerVR SGX 543MP**，CPU 四核 444 MHz，可用内存约 330 MB。
而游戏 CG 是 **1920×1440 RGBA**，解码后每张 11 MB，而游戏 virtual 分辨率
只有 1365×768 —— 多出来的像素纯属浪费。

再加上 `renpy.py` 里对 Vita 写死了：

```python
os.environ["RENPY_LESS_MEMORY"] = "True"
```

这个开关会关掉 `renpy/display/im.py` 里的 `keep_preloading`，
也就是**图片不做后台预加载**，每张都得现解码 → 明显卡顿。

### 优化 1：降采样图片（收益最大）

```powershell
python tools/optimize_images.py <src.rpa> <dst.rpa> --max-w 1366 --max-h 768
```

做三件事：
1. 超过 1366×768 的等比缩到框内（1920×1440 → 1024×768）
2. alpha 全 255 的 RGBA 转 RGB（省 25% 内存）
3. PNG 用 optimize + compress_level 9 重存

实测（PC 上）：

| | 原始 | 优化后 |
|---|---|---|
| 图片总大小 | 144.5 MB | 42.3 MB（省 71%） |
| 单张解码+缩放 | 83.6 ms | 19.4 ms（**快 4.3 倍**） |

Vita 的 CPU 慢得多，这个差距会放大到几百毫秒的级别。

### 优化 2：删掉用不到的翻译

游戏自带 5 套完整翻译（en / es / zhcn / zhtw + DLC 的 jp），
每套都是完整的 `script.rpyc` 副本，启动时**全部**会被解析。

```powershell
python tools/rpa_tool.py filter game/archive.rpa game/archive_new.rpa --drop 'tl/en/,tl/es/,tl/zhtw/'
```

实测 PC 上 `Loading script` 1.69s → 0.73s。Vita 上对应的 71.98s
按比例会降到 30~40s。

### 优化 3：Ren'Py 配置调优

编译成 `psv_perf.rpyc` 放进 `game/`：

```python
init -9 python:
    config.image_cache_size_mb = 64      # 默认 300，Vita 给不出来
    config.hard_rollback_limit = 20      # 默认 100，弱 CPU 上开销明显
    config.predict_statements = 16       # 默认 32，慢存储上反而拖累
    config.autosave_frequency = None     # 自动存档是完整序列化+写卡，顿挫明显
```

### 综合效果

| | 优化前 | 优化后 |
|---|---|---|
| game 目录 | 298 MB | 194.5 MB |
| 单张 CG 解码 | 83.6 ms（PC） | 19.4 ms（PC） |
| 启动加载脚本 | 71.98s（真机） | 待测 |

### 关于重打包 rpa 的坑

> **2026-10-31 已修好**，工具改用 `tools/rpa_tool.py`。下面是踩过的坑，留作参考。

Vita 运行时是 **Python 2.7**。Python 3 的 pickle 有两个不兼容点：

1. `bytes` 会写成 `_codecs.encode`，Py2 解不了
2. `str` 会写成 `SHORT_BINUNICODE`，Py2 解成 `unicode`，而 Ren'Py 按 `str` 比较路径

**真正致命的第三个坑（这才是之前一直失败的原因）**：
index 里每个条目是 `(offset, length, prefix)`，`prefix` 如果是 Python 3 的
`str ''`，pickle 后在 Py2 里是 `u''`。Ren'Py 的 `loader.SubFile.read()`
会做 `self.start[0:n] + file.read(...)`，`u'' + 二进制字节`
走 unicode 解码 → **数据被破坏**，报错是
`Exception: Could not load from archive screens.rpyc.`，看不出跟 prefix 有关。

修法：**prefix 用 `bytes b''`**。Py2 读出来是 `str ''`，拼接正常。

另外这个合集里的 `.rpa` 有个非常规之处：**offset 和 length 都和 key 做了 XOR**
（标准 RPA-3.0 只 XOR offset）。Ren'Py 的 `read_index` 两个都 XOR，
所以照做即可。

## 7.10 RPA 重打包：为什么必须修它

不修 `rpa` 就只能改 `game/` 下的零散文件，没法：
- 降采样图片（性能优化的最大头）
- 删掉用不到的翻译（启动时间）
- 把补丁直接打进包里（省一个补丁文件）

`tools/rpa_tool.py` 支持 `list / extract / pack / filter`，
`tools/optimize_images.py` 建立在它之上。
