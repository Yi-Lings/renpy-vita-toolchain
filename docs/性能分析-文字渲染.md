# 性能分析：文字渲染是唯一瓶颈

> 2026-10-31 ~ 11-01，Angel Sex Pet / PS Vita 3.65
> 本文记录**实测数据**和**由此推出的结论**。
> 根因已确认并修复（见 §0.1）；仍属推测的地方在文中明确标注。

---

## 0. 一句话结论

**操作卡顿约 90%（实测 89–99%）来自文字渲染。**

根因已确认并修复：**FreeType 读字体走 Python 回调，每次读字形都 seek+read `.rpa` 里的字体文件**。
修复后整帧 **10.23s → 2.76s（3.7×）**，文字渲染 **9.12s → 1.64s（5.6×）**。

---

## 0.1 修复效果（真机实测）

修复手段见 [方向 1](#方向-1已完成-把字体整块读进内存不再流式读-rpa)：
把字体类文件整块读成 `io.BytesIO`，不再流式读 `.rpa`。

| 指标 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| **进设置 整帧** | **10.23s** | **2.76s** | **3.7×** |
| 进设置 文字渲染 | 9.12s | **1.64s** | **5.6×** |
| **再进菜单 整帧** | **8.12s** | **2.79s** | **2.9×** |
| 再进菜单 文字渲染 | 7.41s | **2.09s** | **3.5×** |
| `开始游戏`（size 24，4 字） | 2.39s | **0.50s** | 4.8× |
| `圣天使夏洛…`（size 22，标题） | 3.45s | **0.57s** | 6.1× |
| `@CherryKissGames`（size 16，16 字符） | 2.11s | **0.48s** | 4.4× |

修复前后日志原文对照：

```
修复前：PSV FRAME 10.23s | get=8(miss=5) 1.01s | text=10 9.12s | tex=0 0.00s
修复后：PSV FRAME  2.76s | get=8(miss=5) 1.01s | text=10 1.64s | tex=0 0.00s

修复前：PSV FRAME  8.12s | get=27(miss=4) 0.40s | text=35 7.41s | tex=0 0.00s
修复后：PSV FRAME  2.79s | get=27(miss=4) 0.40s | text=35 2.09s | tex=0 0.00s
```

**根因确认**：只有字体加载方式变了，`get=`（图片解码）数字一字未动，
`text=` 掉了 3.5–5.6 倍 —— 变量唯一，因果成立。

内存代价：6 个字体共 **28.77 MB** 常驻（详见下方「方向 1」）。

> 这说明每次 `Text.render` 里有大量**非计算性**的开销——I/O。

## 2. 根因分析

### 2.1 FreeType 通过 Python 回调读字体

`renpy/text/ftfont.pyx:123-157`：

```cython
cdef unsigned long io_func(FT_Stream stream, unsigned long offset,
                           unsigned char *buffer, unsigned long count):
    face = <FTFace> stream.descriptor.pointer
    f = face.f                          # ← 字体文件对象

    if face.offset != offset:
        f.seek(offset)                  # ← 每次都要 seek
        face.offset = offset

    if count != 0:
        buf = f.read(count)             # ← 每次都要 read
        cbuf = buf
        for i from 0 <= i < count:
            buffer[i] = cbuf[i]         # ← 还要逐字节拷进 C buffer
```

FreeType 拿到的是 `FT_OPEN_STREAM`（`ftfont.pyx:208`），**所有**字体数据都走这个回调。

### 2.2 而这个文件对象是 `.rpa` 里的 SubFile

`renpy/text/font.py:615` → `font_file = renpy.loader.load(fn)`。
字体在 `gui_resource.rpa` 里，所以返回的是 `SubFile`。

`renpy/loader.py:475-497`：

```python
def read(self, length=None):
    if self.f is None:
        self.open()                     # ← open("gui_resource.rpa", "rb")
    ...
    rv2 = self.f.read(length)           # ← 真实磁盘 I/O
```

### 2.3 叠加起来

**每读一个字形轮廓 = Python 回调 + `seek()` + `read()` 一次 14.9 MB 的 RPA 文件。**

CFF 字体读一个字形通常要读多处（charstring INDEX、subr INDEX、hmtx 等）。
按每字形 3–5 次读取**估算**，一句 32 字的台词 ≈ **96–160 次磁盘 I/O**。

在 Vita 的存储卡上，单次 seek+read 若耗时 5–10 ms，
就是 **0.5–1.6 秒** —— 与实测的 1.05–1.52s 吻合。

### 2.4 这个解释能对上所有现象

| 现象 | 解释 |
|---|---|
| `1.3.2` 五个 ASCII 要 0.56s（112 ms/字） | 与字形复杂度**无关** —— ASCII 并不比汉字便宜 |
| 汉字台词 42–48 ms/字，反而**比 ASCII 便宜** | 说明瓶颈不是字形复杂度，而是该字形触发了多少次字体文件读取 |
| 每字成本在 20–598 ms 之间大幅波动 | 取决于字形在 CFF 里的位置与读取次数 |
| 同一字号下 0.40s → 1.33s → 1.52s | 每句都是新的一批字形；`ftfont.pyx:262` 的字形缓存只有 256 项（`index & 255`），装不下中文字形集合 —— **推测**，未单独验证 |
| 进设置 10 秒（35 个文本） | 35 个文本各自触发一批 I/O |
| 文字占 89–99%，GL 只占 0.2s | 开销在 CPU 侧读取字体，不在 GPU |
| 图片解码只占 10% | 图片整块读一次，字体是**碎片化**读很多次 |

> **重要**：数据并不支持「汉字比 ASCII 贵」这种直觉。
> 实测 ASCII 反而更贵（112–132 ms/字 vs 汉字 42–48 ms/字），
> 这正说明问题不在光栅化，而在 I/O 次数。

### 2.5 验证结论：已确认

**修复后文字渲染降 3.5–5.6 倍，图片解码数字完全不变** —— 变量唯一，因果成立。

实测内存占用（`PSV FONT MEM`）：

```

gui/font/SourceHanSansSC-Regular.otf       3.95 MB
```

⚠ **`dlc_japanese` 那个字体 16.18 MB，占了一半以上。**
它只用来渲染语言菜单里的「日本語」一个按钮（`splashscreen.rpy:76` 的内联
`{font=dlc_japanese/...}`），却因为没做子集化而拖慢首次使用（日志里

## 3. 已排除的假设（都有实测依据）

| 假设 | 结论 | 依据 |
|---|---|---|
| 垃圾回收 | **排除** | `PSV GCTEST full collect = 0.96s`，且不在慢帧内 |
| 图片解码 | **修复前排除 / 修复后回升** | 修复前只占 10%（1.01s / 10.23s）；**修复后占 37%**（1.01s / 2.76s），已成第二大项，见方向 3 |
| 纹理上传 | **排除** | 全程 `tex=0` |
| 慢特效（MatrixColor / AlphaMask / blur） | **排除** | 扫遍游戏全部 rpy，一处都没有 |
| 文字排版缓存被清空 | **排除** | 放大到 120 后 `TEXTCACHE new=35`，从未接近上限，耗时不变 |
| 字体格式 CFF vs TrueType | **排除** | PC 实测 CFF 0.039ms/字，50 倍折算仍差 24 倍 |
| 描边层数 | **影响很小** | 只有 3 处有 outline，对话正文没有；设置页 35 个文本里只有 1 个是标题 |
| developer 模式 | **排除** | 游戏没设，默认关闭 |
| gl2 渲染器 | **不可用** | Vita 无 FBO（日志 `copy RTT`），用 gl2 会崩 |
| `image_cache_size_mb` 调大 | **无效** | Vita 运行时 `Cache.init()` 写死 `26214400`（25.0 Mpx） |

## 4. 优化方向

### 方向 1（已完成 ✅）：把字体整块读进内存，不再流式读 `.rpa`

**状态**：已实装为 `patches/psv_fontmem.rpy`，真机验证 **整帧 3.7× 提升**。

**做法**：patch `renpy.loader.load`，字体类文件返回 `io.BytesIO` 而不是 `SubFile`。

```python
init -9 python:
    import io
    import renpy.loader as _ld

    _orig_load = _ld.load
    _FONT_EXT = (".ttf", ".otf", ".ttc", ".otc")

    def _psv_load(name, *a, **kw):
        rv = _orig_load(name, *a, **kw)
        try:
            if name.lower().endswith(_FONT_EXT):
                data = rv.read()          # 整块读进内存
                rv.close()
                return io.BytesIO(data)
        except Exception:
            pass
        return rv

    _ld.load = _psv_load
```

**为什么有效**：`io_func` 的 `f.seek()` / `f.read()` 从「磁盘 I/O」变成「内存拷贝」。

**实测收益**：整帧 **10.23s → 2.76s**，文字 **9.12s → 1.64s**（见 §0.1）。

**代价**：字体常驻内存 **28.77 MB**（6 个字体）。Vita 约 330 MB 可用，可接受。
其中 16.18 MB 是未子集化的日文字体，见方向 2。

**风险**：低。纯 Python，不动引擎二进制；`load_face` 只做 `seek(0,2)/tell/seek(0,0)`，`BytesIO` 全支持。

---

### 方向 2（下一步首选）：子集化 16 MB 的日文字体

`dlc_japanese/font/SourceHanSans-Regular.otf` 是 **16.18 MB 完整字体**，
只用于语言菜单的「日本語」按钮（`splashscreen.rpy:76` 的内联字体标签）。

- 子集化后约 1 MB，**省 15 MB 内存**
- 首次使用从 1.74s 降到约 0.2s（日志里那条 `PSV TEXT 1.74s` 就是它）
- 做法同已有 `subset_font.py`，字符集取 `dlc_japanese.rpa` 里 `tl/jp/*.rpy` 的全部用字

**注意**：这**不是**「预渲染字体」（已被否决），只是删掉用不到的字形。

**风险**：低（工具和流程已成熟，注意字符集全覆盖 —— 见 RULES 铁律 11）。

---

### 方向 3：继续压低图片解码（现在已与文字同一量级）

修复后进设置的构成变成：

```
PSV FRAME 2.76s = get 1.01s + text 1.64s + 其他 0.11s
```

**图片解码 1.01s 现在占了 37%**，8 次 `cache.get` 里 5 次未命中。

可选：
- GUI 图再降一档（1024×768 → 960×544，正好等于 drawable 分辨率）
- `gui/overlay/*.png` 这类大 RGBA 图转 JPEG（若不需 alpha）

---

### 方向 4：减少同屏文本控件数

设置页一帧 35 个文本。修复后每个约 60 ms（原来 212 ms），仍有优化空间。
若能合并静态标签（例如把「音量」「文字速度」这类固定标签合成一张背景图），
文本数减半，耗时大致线性下降。

**代价**：要改 `screens.rpy`，工作量大，且影响后续换语言。

---

### 方向 5：减少 `{font=...}` 内联切换

内联字体标签会引入**额外的字体文件**（`fa.ttf`、日文字体），每个都要单独建立 face + 流。
`fa.ttf` 只用来画 FontAwesome 图标。

**可选**：把图标改成图片（`add "gui/icon_settings.png"`），彻底去掉 `fa.ttf`（省 0.36 MB）。

---

### 方向 6（收益小，不建议单独做）：菜单标题描边 4 层 → 1 层

只影响 `game_menu_label_text`（每屏 1 个）。设置页 35 个文本里只占 1 个，
乐观估计省 5–15%。**视觉上描边会明显变薄。**

## 5. 后续验证顺序

1. ✅ **方向 1 已完成**，整帧 10.23s → 2.76s，根因确认。
2. **方向 2（子集化 16 MB 日文字体）** —— 省 15 MB 内存 + 消掉首次 1.74s。

4. 剩余文字开销（1.64s / 10 个文本）已属正常量级，继续压收益递减。

## 6. 附：探针使用说明

`patches/psv_diag.rpy`（v8）会输出：

| 行 | 含义 |
|---|---|
| `PSV FRAME <s> \| get=<n>(miss=<m>) <s> \| text=<n> <s> \| tex=<n> <s>` | 一帧内各阶段耗时 |
| `PSV TEXT <s> size=<字号> style=<样式> '<内容>'` | 单个文本的耗时与内容 |
| `PSV TEXTCACHE size=<上限> new=<n> old=<n> vnew=<n>` | 排版缓存使用量 |
| `PSV FONT MEM <文件> <MB>` / `total: <n> fonts` | 字体整块入内存（方向 1 生效标志） |
| `PSV IMG <s> <图片>` | 单张图片解码超阈值 |
| `PSV PAD: <按键名>` | 手柄按键名（核对映射用） |
| `PSV CFG: ...` | 缓存上限 / less_mem / 配置快照 |

⚠ `renpy.display.draw` 在 `init` 阶段是 `None`，纹理探针必须延迟到第一次交互再装。

⚠ **`psv_diag` 是诊断探针，不进发布包** —— 它包装了 `Text.render`、
`render_screen`、`cache.get`、`loader.load`，每次调用都要计时，在 444MHz 上本身就有可观开销。
发布构建（`dist/AngelSexPet_v4/`）里已排除，只保留 `psv_fontmem` / `psv_keys` /
`psv_perf` / `psv_input` / `psv_skip_telemetry`。
